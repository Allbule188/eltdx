# 用 eltdx 替代 cloud_server 的 TDX 数据获取

> 计划文档 · 2026-09-22
> 范围：**只替换 tqcenter 公式引擎那条链路**。minishare（竞价）、龙虎/开盘啦（板块/涨停/题材）保持原样。
> 依据：`eltdx/infor/eltdx-实测与使用要点.txt` 与 `eltdx/infor/scripts/` 下的实测脚本。

---

## 1. 替换什么、不替换什么

### 现状：cloud_server 有 4 条互相独立的数据源

| # | 数据源 | 技术形态 | 载体 | 本次是否替换 |
| --- | --- | --- | --- | --- |
| **A** | **通达信 tqcenter 公式引擎**（公式 `L2资金四档`） | 本地 Windows 插件 | 采集机 `C:\tdx1` | ✅ **替换** |
| B | 龙虎 VIP（longhuvip.com） | TCP protobuf + HTTP | `crawler/` | ❌ 保持 |
| C | minishare（竞价 `rt_bid_ms`） | HTTP SDK | `crawler/pre_market/` | ❌ 保持 |
| D | 选股宝（炸板池） | HTTP | `server/data/zhaban_pool_cache.py` | ❌ 保持 |

**A 与 B/C/D 完全正交** —— 替换 A 不影响其它三条链路的任何逻辑。

### A 链路的完整数据流

```
[采集机 Windows]
  tdx_bridge/poll_loop.py
    └─ tq.refresh_cache("AG", force=True)
    └─ tq.formula_process_mul_zb(formula_name="L2资金四档")
         → 一次调用返回全 A 股 33 个公式字段
    └─ combine()  补 名称 / 净成占比 / 竞成比
    └─ POST {MERGE_URL}/receive

[merge_server]  tdx_bridge/merge_server.py (Flask + SQLite)
    └─ 按日分库 tdx_YYYYMMDD.db，表 tdx_data (36 列 + 元数据列)
    └─ GET /query/latest | /query/codes | /query/window | /worker/status

[cloud_server 主体]
  server/services/tdx_bridge_setup.py
    └─ 每 15s 拉 /query/latest → FullStockCache.update_tdx_data()
  server/data/tdx_data_reader.py
    └─ 中→英字段映射（_FIELD_MAP，35 条）
  → 策略3 / 策略4 / 情绪 / 板块资金图 / 中证1000 等全部下游
```

## 2. 核心设计：只换生产端

**merge_server 的 `/receive` 接口、36 字段 schema、`/query/*` 查询接口全部保持不变。**

```
替换前:  [Windows采集机 + tqcenter] ──POST /receive──> merge_server ──> 下游（不变）
替换后:  [任意机器 + eltdx]        ──POST /receive──> merge_server ──> 下游（不变）
```

**收益**：

- 下游**零改动**（`TdxDataReader`、`FullStockCache`、所有策略都不用动）
- 可以**双跑对比**（两条链路同时往 merge_server 写，用不同的 `run_id` 前缀区分）
- **回滚成本极低**（把 poll_loop.py 重新拉起来即可）

**换来的东西**：

- 不再需要 Windows 采集机、不再需要装通达信客户端、不再依赖 `tqcenter` 插件
- 采集端可以跑在 Linux / macOS / 任意云主机
- 数据获取逻辑变成纯 Python，可读可测

## 3. 字段覆盖度评估（已实测）

目标：`tdx_data` 表的 36 个字段（33 公式 + 名称/净成占比/竞成比）。

### 3.1 完全覆盖 —— 23 个

| 公式字段 | eltdx 来源 | 备注 |
| --- | --- | --- |
| 现价 / 涨幅 / 成交额 / 成交量 | `quotes.refresh()` | — |
| 开盘金额 | `quotes.refresh().open_amount_yuan` | — |
| 涨速 / 量涨速 / 两分钟金额 / 开盘抢筹 | `0x054b` 分类行情 | ⚠️ 需翻页，见 §3.5 |
| 超大单/大单/中单/小单 **净额**（4） | `money_flow.main_*_net` | 逐档已校验 |
| **主力净额** | `money_flow.main_net` | = 超大+大，精确成立 |
| 涨停委买额 | 五档买一 `bid1.price × volume × 100` | 口径待对撞 |
| 流通市值 / 换手率 | `corporate.finance_batch()` 组装 | 单位为元/百分数 |
| 均价 | 成交额 ÷ 成交量 | — |
| 昨日涨幅 / 昨日成交额 | `bars.get(period="day", count=2)` | — |
| 名称 | `codes.latest_stock_list()` | — |
| 净成占比 / 竞成比 | 本地派生 | 公式见 §3.4 |

### 3.2 主动买卖 8 字段 —— 用 `buckets` 算出双边值

**eltdx 不是只有净额。** SDK 暴露的 `main_*_net` 是「买 − 卖」算好的**差值**；
原始的双边买卖在**公开字段 `buckets`** 里（16 个值 = 8 组买/卖对）。

转换公式（官方文档给出，已逐位验证）：

```text
金额 = buckets[i] / 50000 × total_amount

档位       买入下标   卖出下标
超大单         0          1
大单           4          5
中单           8          9
小单          12         13
```

**实测校验**（sz300207，2026-09-22）：

| 档位 | 主动买 | 主动卖 | 净额（SDK 直接给） | 校验 |
| --- | ---: | ---: | ---: | :--: |
| 超大单 | 159,208,475 | 266,468,218 | -107,259,743 | ✓ |
| 大单 | 224,303,417 | 278,039,306 | -53,735,889 | ✓ |
| 中单 | 511,429,964 | 529,119,795 | -17,689,831 | ✓ |
| 小单 | 619,537,850 | 440,852,387 | 178,685,463 | ✓ |

**决策：8 个字段全部使用 `buckets` 算出的双边值。**

适配器 `eltdx_tdx_adapter.py` 已实现该映射（`TIER_BUCKETS`），无需新代码。

#### 3.2.1 为什么双边值可用：关键恒等式

```
主动买 − 主动卖 = 净额
```

前端测试代码里找到了这条恒等式在下游的确切用法
（`test/test_csi1000_flow_sync.py:143-147`）：

```python
assert values["super_active_net"]  == (30 - 10) + (12 - 4)   # 超大单主动买 − 主动卖
assert values["large_active_net"]  == (25 - 5) + (9 - 3)
assert values["medium_active_net"] == (15 - 3) + (6 - 2)
assert values["small_active_net"]  == (8 - 2) + (4 - 1)
```

**下游用的是「差值」，而 eltdx 的双边值差值 = 真净额（四档全部精确通过校验）。**

各下游的实际用法：

| 下游 | 实际用什么 | 双边值是否可用 |
| --- | --- | --- |
| **板块资金图** | 主动买 − 主动卖 = 净额 | ✅ **差值精确正确** |
| **情绪词条** | 主动买的**绝对值和** | ⚠️ 见 §3.2.2 |
| **策略A回测** | 主动买绝对值 | 🗑️ **本轮删除**（见 §6 阶段 1） |

#### 3.2.2 唯一需要注意的：情绪词条的绝对值

`server/data/emotion_service.py:288,303`

```python
'big_buy': _to_float(fields.get('cdd_active_buy')) + _to_float(fields.get('dd_active_buy')),
'mid_buy': _to_float(fields.get('zd_active_buy')) + _to_float(fields.get('xd_active_buy')),
```

用的是**绝对值和**，不是差值，所以受量级影响。

⚠️ eltdx 的双边值是**双边记账**：每笔成交在买方档位和卖方档位**各记一次**，
所以 `Σ主动买 = Σ主动卖 = 成交额`。而公式的主动口径是**互斥**的
（内盘/外盘，两侧合计才等于总量）。**因此 eltdx 的主动买/卖量级大概率偏大。**

影响程度取决于下游判定方式：

- 情绪词条判的是「**环比 +10%**」。若两边只差一个常数倍，环比不变 → **不受影响**
- 若分解方式不同导致轨迹不同，环比会变 → **需要复核**

**处置**：保留双边值、不填 0，**在对撞时重点验证这条链路**（见 §5）。

#### 3.2.3 为什么不用填 0

| 方案 | 板块资金图 | 情绪词条 | 策略A |
| --- | --- | --- | --- |
| 填 0 | ✅ 0−0=0，数值正确但**丢信号** | ❌ 0+0=0，**完全无信号** | 已删 |
| **双边值（采用）** | ✅ 差值=净额，**正确且有信号** | ⚠️ 有信号，量级可能偏大 | 已删 |

**填 0 反而更糟** —— 它把本来完全正确的板块资金图也一起毁掉了。

### 3.3 拿不到 —— 4 个

| 字段 | 类型 | 原因 | 填充 |
| --- | --- | --- | --- |
| 主动买成交额 | REAL | 请看下方说明 | **`0`** |
| 主动卖成交额 | REAL | 同上 | **`0`** |
| 短期形态 | TEXT | 通达信公式专有枚举（1~14），无复现路径 | **`""`** |
| 中期形态 | TEXT | 同上 | **`""`** |

**为什么这两个成交额不能像 §3.2 那样用双边值：**

它们是**总量级**字段（不分档），而 eltdx 的双边求和恒等于成交额：

```text
Σ四档主动买 = Σ四档主动卖 = 成交额    （双边记账的必然结果）
```

两个值都等于成交额，**没有信息量**。所以这两个保持 `0`。

（若要近似公式口径的「外盘金额」，可用 `外盘手数 × 均价`，但那是估算，
本轮不引入，仅在展示层可接受时再考虑。）

**形态两个字段**已穷举全仓确认：只用于「数据库页」两列展示，`strategy/` 下 0 引用。
因是 TEXT 列，填 `""` 而非 `0`（客户端查表渲染会显示为空）。

**统一原则：所有拿不到/不能用的字段一律显式填值（REAL 填 `0`、TEXT 填 `""`），
不用 NULL、不省略列 —— 保证 `tdx_data` 表结构与下游代码零改动。**

### 3.4 可实现但未写 —— 1 个

- **三日换手率**：需要 3 日历史换手率。用 `bars` + `finance_batch` 可算，工作量约半天。

### 3.5 成本问题：涨速等 4 个字段

`涨速` / `量涨速` / `两分钟金额` / `开盘抢筹` **只在 `0x054b` 分类行情里**，而：

- 页大小**硬卡 80 条**（传 200/500/1000 都只返回 80）
- **不能按代码过滤** —— 是排序榜单，要指定股票必须翻完整个市场

```
全市场 5575 只 → 70 次请求/轮
```

**对比**：公式引擎这 4 个字段是白送的（同一次调用）。

**对策**：
- 方案 a：每轮翻 70 页（实测 `0x054b` 单页约 40-55ms，70 页 ≈ 3-4 秒）—— **可接受**
- 方案 b：只在需要的时段翻（如早盘 09:30-10:00，`开盘抢筹` 的语义窗口）
- 方案 c：不翻，这 4 个字段从 eltdx 链路降级（需确认下游依赖强度）

**建议先做方案 a**，实测总成本见 §4。

## 4. 性能预算

### 4.1 数据获取成本（实测）

| 数据 | 方案 | 实测耗时 |
| --- | --- | --- |
| 资金流（四档 + 主力净额） | 10 连接固定分工 | **22.2 秒/轮** |
| 同上 | 20 连接 | 12.4 秒/轮 |
| 同上 | **40 连接** | **6.8 秒/轮** |
| 五档 / 现价 / 开盘金额 | `quotes.refresh` 批量（100/批） | ~0.9 秒/轮 |
| 涨速 等 4 字段 | `0x054b` 翻页 70 次 | ~3-4 秒/轮 |
| 流通股本 / 昨日数据 | 低频（开盘前拉一次即可） | 一次性 |

**合计约 10-15 秒/轮**（40 连接 + 五档 + 分类行情），可做到与公式引擎相近的节奏。

### 4.2 与现状的关键差异

| | 公式引擎（现状） | eltdx |
| --- | --- | --- |
| 调用次数 | **1 次**拿全市场 | 数千次（每只一次往返） |
| 依赖 | Windows + 通达信客户端 | `pip install eltdx` |
| 主站速度波动 | 无（本地客户端） | **不同主站差 5 倍**（已实测） |
| 数据一致性 | — | `pool_size>1` 会 A/B 交替，必须固定连接归属 |

### 4.3 ⚠️ 必须处理的三个坑

**坑 1：主站之间速度差 5 倍**

```
同配置（10 连接 × 558 只），不同主站:
  124.71.187.122   13.5 ~ 17.6 s   快
  123.60.84.66     90.7 s          慢
  81.71.32.47      96.6 s          慢
```

而 eltdx 自带的 `probe_hosts` **只测 TCP connect 延迟，不反映业务吞吐**。
→ 用 `infor/scripts/pick_fastest_host.py`（真实请求测吞吐），**每次启动前跑一次**。

**坑 2：多连接会导致数据 A/B 交替**

```
pool_size=1  采样46次  A/B交替 0 次    ← 干净
pool_size=2  采样45次  A/B交替 6 次    ← 交替
```

→ 必须用「N 条连接各自固定负责一批股票」的模式（见 `make_pinned_clients` / `sweep_parallel`），
  且 **N 条连接全部固定到同一台主站**（否则跨连接时刻偏差污染板块聚合）。

**坑 3：`money_flow.daily(codes)` 是逐股往返，不是真批量**

```
实测均摊 ~43ms/只，严格线性（1只47ms / 100只4292ms / 200只8563ms）
```

源码用 `ThreadPoolExecutor`，但每只股票单独发一个请求。
→ 单连接串行跑全市场 = 240 秒，必须用多连接固定分工。

## 5. 验证方案（**替代的前置门槛**）

### 5.1 数值对撞 —— 决定成败的一步

**必须确认 eltdx 的数值与公式引擎一致**，否则换源会静默改变策略输出。

**工具**：`infor/scripts/eltdx_vs_cloudserver.py`

```bash
# ① 采集机上导出 cloud_server 侧
python eltdx_vs_cloudserver.py --export-cs --out cs.json

# ② 有 eltdx 的机器上导出（**必须收盘后**，两边数据都已冻结）
.venv/bin/python infor/scripts/eltdx_vs_cloudserver.py --export-eltdx --out eltdx.json

# ③ 对比
.venv/bin/python infor/scripts/eltdx_vs_cloudserver.py --compare cs.json eltdx.json
```

**判读标准**（脚本已内置）：

| 相对误差 | 结论 |
| --- | --- |
| < 1% | 口径一致，可替代 |
| 1~5% | 轻微差异，需人工判断 |
| > 5% | 口径不同，不可直接替代 |

**重点看**：`主力净额` / `四档净额` / `四档主动买卖` —— 这几组是硬门槛。

### 5.2 若口径不一致的处置

按 §3.2 的决定，**8 个主动买卖字段一律用 `buckets` 双边值**，不因对撞结果改填 0。
但对撞结果仍决定「要不要额外处理情绪词条」：

| 对撞结果 | 处置 |
| --- | --- |
| **净额一致**（差值口径相同） | ✅ 双边值直接可用。**重点复核情绪词条的环比**是否仍成立（§3.2.2） |
| **净额也不一致** | 🔴 **放弃替换**，或做线性标定（需评估，风险高） |
| 只有形态 / 成交额字段缺 | **可接受** —— 形态零策略依赖、两个成交额仅展示列，按 §3.3 填 `""` / `0` |

> 对撞时务必区分三类字段：
>
> - **净额 5 个**（§3.1）→ eltdx 有且已校验，**对撞决定整体成败**
> - **主动买卖 8 个**（§3.2）→ 用双边值；对撞只影响情绪词条要不要额外处理
> - **拿不到 4 个**（§3.3）→ 无论对撞结果如何都填 `0` / `""`

### 5.3 双跑期

验证通过后，**两条链路并行跑一段时间**，用 `run_id` 前缀区分：

- eltdx 写入 `run_id = "eltdx_<date>_<time>_r<n>"`
- 公式引擎保持 `run_id = "<date>_<time>_r<n>"`

对比两边的**字段级差异分布**（不只是均值），跑满至少一个完整交易日。

## 7. 风险清单

| # | 风险 | 影响 | 对策 |

| 1 | **净额口径与公式不一致** | 🔴 板块资金图 4 指标、中证1000、策略4 的资金字段全部受影响 | **阶段 2 对撞决定**；不一致则放弃替换或做标定 |

## 8. 附：代理（本次不做，备查）

eltdx **不支持代理**（`TdxClient` 无 proxy 参数；源码里的 `PinnedTransportProxy` 是"固定连接槽"不是网络代理；Rust 引擎直连 `TcpStream`）。

**只有 F10（7615）支持** —— 走 urllib，设 `HTTPS_PROXY` 即可。

**7709 若将来需要走代理**：用本地 relay（`infor/scripts/tdx_proxy_relay.py`），
eltdx 指向 `127.0.0.1:17709`，relay 通过 SOCKS5/HTTP 转发。实测开销在噪声范围内。
