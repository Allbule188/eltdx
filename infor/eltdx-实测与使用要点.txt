1. 项目定位与能力边界
================================================================================

定位
  Python API、Rust 驱动的通达信数据客户端。
  - 7709 : TCP 长连接，管行情（代码表 / 快照 / K线 / 分时 / 成交 / 竞价 / 财务）
  - 7615 : HTTP POST，管 F10（公司资料 / 题材 / 财务报表 / 公告 / 研报）

目标用户
  Python 量化研究者、数据工程开发者、协议研究者

能力范围（已实测可用）
  [OK] 代码表          27934(sh) + 24284(sz) + 383(bj)
  [OK] 五档快照        含买卖五档
  [OK] K线             日线/多周期，支持 qfq/hfq 复权，支持 all_pages 全量
  [OK] 分时            当日 / 历史日期
  [OK] 逐笔成交        当日 / 历史日期
  [OK] 集合竞价        0x056a，支持当日和历史
  [OK] 股本变迁/财务   0x000f / 0x0010
  [OK] 涨跌停限制      0x0452
  [OK] F10 / 题材      7615，30+ 方法
  [OK] Helpers         场景级组合封装（连板天梯/短线指标/题材强度等）

明确的能力边界（拿不到的）
  [NO] 十档盘口        Level-2 数据，免费源没有
  [NO] 逐笔委托队列    只有逐笔成交，没有委托流水（挂单/撤单）
  [NO] 实时推送        WebSocket subscribe 拿不到增量（见第 8 节）
  [NO] 亚秒级刷新      3 秒是数据源天花板（见第 7 节）

返回形态
  全部为 frozen dataclass，无 pandas / NumPy 依赖。
  单 code 传参 -> 返回模型对象；传 list -> 返回 {完整代码: 模型} 的 dict。
  转 JSON 用 to_json() / to_jsonable()。

4. API 结构与推荐入口
================================================================================

4.1 唯一入口 TdxClient，按业务域拆成子 API
--------------------------------------------------------------------------------
  client.session      握手 / 心跳 / ping
  client.codes        代码表
  client.quotes       快照 / 五档 / 分类行情 / 增量刷新
  client.resources    服务器文件读取（zhb.zip）
  client.bars         K线（唯一方法 get()）
  client.minutes      分时 / 副图
  client.trades       成交明细
  client.auctions     集合竞价
  client.money_flow   资金流向
  client.corporate    股本变迁 / 复权系数 / 财务
  client.limits       涨跌停限制
  client.workdays     交易日历
  client.f10          7615 F10
  client.helpers      场景级组合封装  <-- 日常最常用

4.2 三种构造方式
--------------------------------------------------------------------------------
  TdxClient(...)                     # 默认真实主站
  TdxClient.from_hosts(...)          # 显式连接池 + 测速（推荐）
  TdxClient.in_memory()              # 内存客户端，仅供测试

4.3 推荐入口（文档与本实测共同确认）
--------------------------------------------------------------------------------
  完整行情     client.helpers.full_quotes(codes)
  五档（更快） client.quotes.refresh(codes, cursors={})   <-- 见 4.4
  K线复权      client.bars.get(code, period="day", adjust="qfq")
  全量K线      client.bars.get(code, period="day", all_pages=True)

  注意：复权请用服务端 adjust 参数。client.corporate.adjustment_factors()
  返回本地 scale+offset，文档明确不承诺逐值精确重建，可能差 0.01~0.02 元，
  仅适合本地审计。

4.4 【重要】拿五档不要用 full_quotes，用 refresh
--------------------------------------------------------------------------------
  实测三个接口的档位数与成本（20 只，盘前）：

    接口                     档位    往返    耗时
    --------------------------------------------------
    quotes.get_snapshots()    1 档     1     63 ms
    quotes.refresh()          5 档     1     64 ms     <-- 最优
    helpers.full_quotes()     5 档     2    119 ms

  full_quotes 内部 = get_snapshots(0x054c, 只有1档) + get_depth(0x0547, 5档)。
  为了拿五档，第一趟 0x054c 完全是白发的。

  refresh() 单趟往返直接返回五档，成本约为 full_quotes 的一半。
  实测两者返回的数据逐字段、逐档位完全一致（差异数 = 0）。

  结论：全市场五档必须用 refresh()，不要用 full_quotes()。


================================================================================
5. 延迟与并发性能
================================================================================

5.1 冷启动延迟（重要坑）
--------------------------------------------------------------------------------
  全新 client 的前 1~2 次调用需建立 TCP + 7709 握手，约 1.2 秒：

    全新 client，连续 6 次:        同 pool 换股票:
      第 1 次: 1287.2 ms            sz300207: 1175.5 ms
      第 2 次:   77.0 ms            sh600000: 1142.7 ms
      第 3 次:  163.3 ms            sz000001:   88.8 ms
      第 4 次:   78.4 ms            sh601318:  121.7 ms
      第 5 次:  130.1 ms
      第 6 次:   70.8 ms

  原因：连接是按需懒建立的（文档："请求懒启动实际分配到的 Slot"）。
  影响：一次性脚本的第一次查询会明显卡顿，这不是代码问题。
       生产环境必须在开盘前完成连接池预热。

5.2 单接口稳态延迟（盘前实测）
--------------------------------------------------------------------------------
  get_snapshots (1档)   中位  45.6 ms   均  60.2 ms   min 30.7  max 150.6
  refresh       (5档)   中位  76.7 ms   均 115.9 ms   min 69.7  max 307.8
  trades.today          中位  69   ms

  5档 / 1档 倍数: 中位 1.68x  均值 1.92x   绝对开销 +31 ms
  说明：第二趟 0x0547 是增量刷新协议，包体比 0x054c 全量快照轻，
        所以不是简单的 2 倍关系。但两趟往返会放大尾部风险
        (1档 max 150ms vs 5档 max 308ms)。

5.3 线程扩展与 GIL 释放（决定性证据）
--------------------------------------------------------------------------------
  N=200 次单条 full_quotes，每档重复 3 次取中位数：

    线程   wall(s)   吞吐(/s)   p50(ms)   并行度(cpu/wall)   加速比
    ------------------------------------------------------------------
      1     25.65       7.8      113.4        0.04           1.00x
      8      2.95      67.7      114.8        0.14           8.68x
     16      1.48     135.2      113.5        0.24          17.35x
     32      0.80     249.3      114.2        0.37          31.97x

  关键读数：
  (a) 32 线程在 8 核机器上拿到 31.97x 加速。若 GIL 在 I/O 期间被持有，
      加速比最多接近 1x。=> GIL 确实释放，py.detach() 真实生效。
  (b) 并行度仅 0.04~0.37，即进程连半个核都没用满 => 纯 I/O 密集。
      加速来自"重叠网络等待"，不是"用上多核"。
      这解释了为什么能超过核数：上限是在途请求数，不是 CPU。
  (c) p50 延迟在并发下几乎不变（113.4 -> 114.2 ms）
      => 连接池没有排队，并发请求真在同时在途。

  线程数甜点：8 线程（= 本机核数）。再高无额外收益。

5.4 批量 vs 线程（真正的性能杠杆）
--------------------------------------------------------------------------------
  同样拉 200 只股票：

    1 次 full_quotes(200 只)        :    320 ms      <-- 基准
    200 次单条 full_quotes, 8 线程  :  4,361 ms      13.6x 慢
    200 次单条 full_quotes, 顺序    : 18,938 ms      59x  慢

  单次调用延迟 vs 批量大小：

    批量   往返数   延迟(ms)   每条(ms)
    ------------------------------------
      1       1      304.9     304.88
     10       1      327.2      32.72
     40       1      150.0       3.75
     80       1      149.8       1.87
    160       2      291.1       1.82

  关键：40 只和 80 只耗时几乎相同（150.0 vs 149.8 ms）。
        延迟由 RTT 决定，与批量大小无关（80 以内）。多塞股票是免费的。

  结论：优先批量，其次多线程。收益差 13~59 倍。

  同样的 10 轮全市场五档，16 线程，同一脚本：

    指标                  盘前 09:19      盘中 10:26        变化
    ------------------------------------------------------------------
    单轮耗时（中位）        0.53 s          0.94 s          1.8x 慢
    吞吐                 10,574 只/s      5,950 只/s        降 44%
    最快 / 最慢          0.45/0.67 s     0.80/1.28 s         --
    连接池预热             2.90 s         12.98 s          4.5x 慢
    覆盖/五档完整/缺档   5574/5574/0     5574/5574/0        无退化
    内存                  12.84 MB        14.31 MB         +1.5 MB

         这不是"盘中活跃度"，本质是 3 秒时钟的采样相位。

7. 【核心】数据源刷新粒度 = 3 秒
================================================================================

  【结论】通达信免费行情（沪深 Level-1）的刷新粒度为 3 秒。
          这不是 eltdx 或通达信的限制，是交易所 Level-1 行情发布标准。
          轮询快于 3 秒没有任何收益。

7.1 服务端时间戳与版本号跳动（10 只活跃股，0.25s 高频轮询 60 秒）
--------------------------------------------------------------------------------
    服务端更新时间戳 update_time_raw 间隔: 中位 3027 ms  (p10 2732 ~ p90 3212)
    版本号 active 间隔                   : 中位 3038 ms
    完整盘口状态(价+量+买卖一)变化间隔    : 中位 3031 ms  (p10 2732 ~ p90 3212)

7.2 轮询周期 vs 召回率（10 只，0.2s 基线采样 90 秒）
--------------------------------------------------------------------------------
    真实更新总数 313 次 / 90s / 10 只 = 每只 0.35 次/秒 = 每 2.86 秒一次

    轮询周期   采样数   召回更新   召回率   漏掉    重复率
    ----------------------------------------------------------
     0.20     3490      313    100.0%     0    91.0%
     0.50     1800      306     97.8%     7    83.0%
     1.00      900      306     97.8%     7    66.0%
     2.00      450      303     96.8%    10    32.7%
     2.50      360      300     95.8%    13    16.7%
     3.00      300      294     93.9%    19     2.0%   <-- 甜点
     3.50      260      258     82.4%    55     0.8%
     4.00      230      229     73.2%    84     0.4%
     5.00      180      178     56.9%   135     1.1%

  读法：
  - 重复率：0.2s 轮询有 91% 是白跑的；1s 轮询 66% 白跑；3s 时降到 2%。
  - 召回率：3s 仍有 93.9%；一旦超过 3.5s 断崖式下跌（82% -> 73% -> 57%）。
  - 拐点精确卡在 3 秒，与 7.1 的服务端间隔完全吻合。

7.3 逐笔成交也是 3 秒（独立协议，独立验证）
--------------------------------------------------------------------------------
  协议 0x0fc5 / 0x0fc6，同一方法实测：

    代码        更新次数   平均间隔ms   中位间隔ms   最小ms   最大ms
    ---------------------------------------------------------------
    sz300207      31        2922       2992      1036     3411
    sh600519      18        4941       3309       345    12232

    中位间隔 3000 ms   p10 2665 ms   p90 5808 ms
    快于 3 秒的比例: 49%    <-- 只是 3 秒时钟的相位抖动，不是"有时更快"
    快于 1 秒的比例:  2%

  两条独立协议（快照 0x0547 / 逐笔 0x0fc5）测得同一个 3 秒。

7.4 逐笔成交的时间戳只到分钟
--------------------------------------------------------------------------------
  TradeTick 字段：
    time_minutes = 634         -> 10:34
    time_label   = '10:34'
    trade_datetime = None      -> 字段位置留了，数据没有

  实测同一分钟内有多笔独立成交（volume 35/21/44/69 手，
  order_count 5~20 笔委托），确认是真实逐笔，
  但协议只给分钟级时间戳，拿不到"10:34:17 成交的"。

7.5 对监控架构的结论
--------------------------------------------------------------------------------
  [错] 关注池 1 秒高频    -> 2/3 请求拿回重复数据，零收益
  [对] 全市场 3 秒一轮    -> 93.9% 召回，2% 浪费，最优解
  [错] 任意快于 3 秒轮询  -> 无论盯几只股票，都是白跑

  3 秒是数据源天花板，对所有股票一视同仁（关注池的股票也不会更新更快）。
  因此"双层架构（关注池高频 + 全市场兜底）"没有意义，唯一起作用的是
  单层全市场 3 秒轮询。

  唯一可优化方向是覆盖面（3 秒内扫完多少只），不是频率。

7.6 资金流 money_flow（0x0ffc）：刷新 ~20 秒
--------------------------------------------------------------------------------
  【结论】资金流刷新节拍 **约 20 秒**，比快照的 3 秒慢约 7 倍。
          按 20~30 秒轮询即可，用 3 秒是纯浪费。

  【口径修正（2026-09-22）】此前本报告写的是「30~40 秒」，**那是误判**。
         原因：单只股票样本只有 14 个变化点，且会漏掉「值不变的那一拍」，
         把 20 秒的节拍记成了 40 秒。改用 10 只股票后（每拍有 5~8 只同时变化，
         不可能漏），节拍清楚地落到 20 秒。详见下面的实测数据。

  --------------------------------------------------------------------------
  2026-09-22 实测 A：10 只 × 0.39s 采样 × 7 分钟
  --------------------------------------------------------------------------
  捕获 20 个「变化事件」，**每个事件的 wall%5 相位全部落在 [1.02, 1.56]**
  —— 只有 0.54 秒宽，而采样分辨率就是 0.39 秒，已接近测量极限：

      1.35, 1.23, 1.43, 1.44, 1.18, 1.25, 1.02, 1.45, 1.19, 1.17,
      1.19, 1.43, 1.29, 1.34, 1.56, 1.04, 1.33, 1.35, 1.39, 1.38

  => **确认存在固定墙钟网格**（随机分布的概率几乎为零）。

  事件间隔（19 个）：
      29.88, 20.19, 20.01, 19.74, 20.08, 24.76, 15.44, 19.74, 14.98, 25.01,
      20.25, 19.85, 20.06, 20.21, 19.49, 20.29, 10.01, 30.05, 19.98
  **12/19 落在 19.5~20.3 秒**，其余是 15/25/30 秒（漏一拍或多一拍）。

  那个 1.3 秒左右的固定相位偏移，很可能是本机时钟与服务端时钟的偏差
  （未验证），不是网格的真实相位。

  --------------------------------------------------------------------------
  2026-09-21 实测 B：单只 × 0.5s 采样 × 8 分钟（旧数据，仅作对照）
  --------------------------------------------------------------------------
    数据              变化次数        中位间隔     平均
    ----------------------------------------------------------
    快照 0x0547       160 次/480s     2.93s      3.00s
    资金流 0x0ffc      14 次/480s    39.88s     33.87s   <- 样本不足，偏高

  --------------------------------------------------------------------------
  其它已确认事实
  --------------------------------------------------------------------------
  * 8 个分档字段（main_* 四档 + main_buy_* 四档）**完全同步**，不存在独立更新。
  * money_flow 的 18 个字段里**没有任何时间戳或版本号**（对比快照有
    update_time_raw / active），所以只能观测「值变化」不能观测「刷新动作」。
    严格说仍有「刷新了但值没变」的理论盲区；因 total_amount 是累计成交额且
    期间持续有成交，该盲区在实盘中可忽略。
  * 在 raw 的 21 个 uint32 里找隐藏计数器：**未找到**。raw[0]/raw[1]/raw[18]
    看似单调小增量，实为累计买卖额，不是独立计数器。
  * 资金流是**四档**（超大单/大单/中单/小单），不是五档；五档是盘口
    （quotes.refresh），两者是不同接口、不同频率（3s vs ~20s）。

  MoneyFlowDaily 的 18 个字段与两套口径，见第 10.16 条。
  多连接 A/B 交替问题，见第 10.15 条。

7.7 资金流全市场扫描：10 连接固定分工（2026-09-22 新增）
--------------------------------------------------------------------------------
  【背景】money_flow.daily(codes) 表面支持批量，但**实现是每只一次独立往返**
         （源码用 ThreadPoolExecutor，然而每只股票单独发一个请求）：

    股票数    耗时      均摊
    --------------------------
        1     47 ms    47.06
       10    453 ms    45.34
      100   4292 ms    42.92
      200   8563 ms    42.82     <- 严格线性 ~43ms/只

    所以在 pool_size=1 下串行跑全市场 = 5575 × 43ms ≈ **240 秒/轮**。

  【解法（用户提出）】A/B 交替的成因是「同一只股票被轮流分到不同连接」。
        若每只股票**永远只从同一条连接取**，就不会交替。

    实现：开 N 个独立 TdxClient，各自 pool_size=1，
          **全部显式固定到同一台主站**（hosts=[host], server_count=1），
          代码按 codes[i::N] 或连续块切分，每只股票只属于一条连接。

  【实测（2026-09-22，主站 124.71.187.122:7709，10 连接 × 558 只）】

    切分方式        墙钟      各 worker(s)
    --------------------------------------------------------------
    连续块         16.8s    [15.4,14.4,14.8,13.6,14.1,13.7,15.9,15.9,15.0,16.8]
    跨步条带       13.5s    [13.0,12.2,12.6,11.6,13.5,12.9,12.0,12.9,13.5,12.3]
    连续块(复测)   17.6s    [17.4,17.4,16.2,16.1,17.5,16.2,15.8,16.2,17.6,15.8]

    => **全市场 5575 只，10 连接固定分工，13.5 ~ 17.6 秒/轮**
       对比串行 240s -> 加速 **14~17x**（甚至优于理论线性的 10x）

  覆盖 5575/5575 = 100%。逐股单调性校验（3 轮）：
    **A/B 回退 0 次**（2767 只单调递增 + 562 只两轮无变化）
    对照 pool_size=2 轮询时出现过 6 次交替。

  【连接数扩展（2026-09-22，主站 43.139.95.83，全市场 5575 只）】

    连接数  每连接  墙钟s   聚合只/s  单连接只/s  相对10连接   理想
    ----------------------------------------------------------------
      10     557   22.3    250.5     25.1      1.00x      1.00x
      20     278   12.4    450.4     22.5      1.80x      2.00x
      40     139    6.8    825.3     20.6      3.29x      4.00x

    单连接吞吐 25.1 -> 22.5 -> 20.6 只/秒，随连接数缓降（轻微争用），
    但总吞吐持续上升：**40 连接可做到全市场 6.8 秒/轮**（对比串行 240s = 35x）。

    [稳定性] 10 连接 × 10 轮：中位 22.2s，标准差 1.57s，波动 23.2%，
             min 19.2 / max 24.3，覆盖 5575/5575 每轮 100%。
             未再出现早期那种 90 秒异常（那是慢主站所致）。

    [轮间变化] 中位 3160 只 / 5575 = 56.7%。
             注意这是「有成交从而资金流变化」的比例，**不是刷新频率** ——
             采样间隔 22s 已大于 20s 网格，每次都覆盖网格点；
             未变的 43% 是那 22 秒内没有成交的低流动性个股。
             10 只活跃股的对照：每个刷新事件 5~8/10 只变化，比例吻合。

  【关键：主站之间的速度差可达 5 倍】
    同样配置（10 连接 × 558 只），不同主站实测：

      124.71.187.122   13.5 ~ 17.6 s    快
      123.60.84.66     90.7 s           慢
      81.71.32.47      96.6 s           慢

    **选主站比优化架构更值钱。** 而 eltdx 自带的 probe_hosts 只测
    TCP connect 延迟，**不能反映真实请求吞吐**——必须实测业务请求才能选对主站。
    见第 7.8 条的主站优选机制。

  【不是 GIL 瓶颈】CPU 占用只有 0.2 核（并行度 cpu/wall = 0.20），纯 I/O。
        10 线程能跑到 9.3x（诊断测试：1 线程 25.4 req/s -> 10 线程 235.8 req/s）。

7.8 主站优选机制（每次运行前自动找最快站点）
--------------------------------------------------------------------------------
  【为什么需要】第 7.7 条实测主站之间慢 5 倍。而 eltdx 的 probe_hosts
        只做 TCP connect 探测（默认 1.2s 超时），connect 快 != 吞吐高。

  【设计】用真实业务请求测吞吐，而不是 TCP 握手：

    1. 从已知主站列表取候选（可用 TdxClient 的排名缓存做初筛）
    2. 对每个候选开 1 条连接，用固定的一小批股票跑 money_flow.daily，
       测"每秒完成多少只"
    3. 取吞吐最高的那台，用 hosts=[host] 固定给全部 N 条连接
    4. 结果落盘缓存（当日有效），下次直接用

  实测脚本见 infor/scripts/pick_fastest_host.py。

  【注意】
    * 探测会真实打请求，候选太多时耗时不短（每台约 2~4 秒）
    * 主站负载随时在变，缓存的"最快"可能几小时后失效；
      长跑任务建议每隔 1~2 小时重测一次，或监控吞吐下降后切换
    * 全部 N 条连接必须固定到**同一台**主站，否则跨连接时刻偏差
      会让板块聚合（把多只股票相加）混入不同时刻的数据

7.9 让 7709 走代理（2026-09-22 新增）
--------------------------------------------------------------------------------
  【结论】eltdx **不支持代理**。已查源码确认：

    * `TdxClient(host=...)` / `TdxClient.from_hosts(...)` 参数里**没有**
      proxy / socks 任何选项
    * 源码里的 `PinnedTransportProxy` 是「固定到某个连接槽」的机制，
      **不是网络代理**（grep "proxy" 会命中它，容易误判）
    * Rust 引擎直接建 `TcpStream`，中间没有代理层
    * **只有 F10（7615）那条支持代理** —— 它走 urllib，
      "Keep urllib's environment proxies"，设 HTTPS_PROXY 即可

  【解法：本地 relay，不改 eltdx 一行代码】
    实测 eltdx **接受任意 host:port 字符串（含 127.0.0.1）**，所以：

        N 个 TdxClient ──> 127.0.0.1:17709 ──[SOCKS5/HTTP]──> 主站:7709

    脚本：infor/scripts/tdx_proxy_relay.py

        pip install pysocks
        python infor/scripts/tdx_proxy_relay.py --proxy socks5://user:pass@1.2.3.4:1080
        # 然后 TdxClient(host="127.0.0.1:17709", probe_hosts=False)

  【实测开销】10 连接经 relay 跑全市场：
        21.9s / 22.9s / 23.3s     （直连同主站对照 22.2s）
        => **relay 开销在噪声范围内**，可忽略。

  【实现坑】第一版 relay 用了非阻塞 socket + selectors，
        结果 `sendall` 在发送缓冲满时抛 `BlockingIOError`，
        被误判成错误而断连（表现为 eltdx 报 "Connection reset by peer"）。
        **改成阻塞 socket + 双向线程**后正常。

================================================================================
9. 架构与 Rust 运行时的实测验证
================================================================================

9.1 分层（单向依赖，unsafe_code = "forbid"）
--------------------------------------------------------------------------------
  TdxClient -> api/* -> SocketTransport
    -> eltdx._native.NativeEngine.execute(command, payload)   PyO3 边界
    -> Rust: CommandRequest -> Supervisor -> Slot task -> TcpStream
    -> CommandResponse -> 紧凑 DTO -> Python dataclass

  protocol 不依赖 Tokio / Python；runtime 不依赖 PyO3；
  python crate 只暴露私有扩展 eltdx._native。

9.2 并发模型
--------------------------------------------------------------------------------
  不是线程池，也不是传统 actor 框架，而是：
  "单所有者 Supervisor + 多线程 Tokio runtime + 异步 Slot"（ADR-0001）

  - 每个 NativeEngine = 1 个后台 OS 线程 + 线程内 1 个 Tokio runtime
  - Supervisor（147 KB，全仓最大模块）是池状态的唯一写入者
  - Slot 是异步 task，每个独占一条 TcpStream，Supervisor 不碰 socket
  - 公平调度预算：每 Slot 单轮最多读 256 KiB / 路由 64 帧 / 产出 4 MiB

9.3 为什么用 Rust（文档的诚实之处）
--------------------------------------------------------------------------------
  核心收益是【连接数可扩到 160+ 而不等比增加线程】+【内存有硬上限】
  + 【解码能并行用多核】。

  但【单连接顺序吞吐与旧 Python 实现基本持平】：
  ACTOR_REFACTOR_RESULT.md 实测 ratio 0.943，低于 95% 目标，
  文档标记为 FAIL 并写明"不伪报为达标"，作为用户批准的例外保留。

  绝对量级：顺序 p50 约 6.2ms，饱和 p50/p99 约 160/175ms。

  本实测印证：单请求延迟 113ms 中绝大部分是等主站回包的网络 RTT，
  Rust 解码再快也快不过它。Rust 换来的不是"更快"，是"更能扩"和"内存有界"。

9.4 线程安全
--------------------------------------------------------------------------------
  - 网络等待走 py.detach() 释放 GIL，等待切片 25ms，实测获 31.97x 加速
  - NativeEngine 是 #[pyclass(frozen)]，可跨线程安全共享
  - 队列满立即抛 PoolBusyError，不持 GIL 无限等
    容量 = pool_size + max_pending_requests（默认 256）
  - fork 不安全：Engine 会检查 PID，fork 子进程不能复用父进程 client
  - diagnostics 读的是缓存快照，完整刷新最多每 25ms 一次

10.15 【重要陷阱】pool_size > 1 会导致数值 A/B 交替
--------------------------------------------------------------------------------
  现象：同一只股票、同一时刻，连续请求返回两个不同的值来回跳。

    1,498,802,432
    1,498,078,208   <- 变小
    1,498,802,432   <- 又变回来
    1,498,078,208   <- 又变小

  对照实验（检测连续三样本的 A/B 交替模式）：

    pool_size=1  采样46次  不同值2  变化1次  A/B交替 0 次   <- 干净
    pool_size=2  采样45次  不同值2  变化7次  A/B交替 6 次   <- 交替

  原因：pool_size>1 时请求轮流打到不同连接，而不同连接上的数据并不同步
        （各自缓存了不同时刻的值），于是来回跳。

  [警告] 这不是服务端修正数据。用单连接时"回退"完全消失：
         资金流单连接单调递增验证: 0/0 次回退。

  影响面：所有依赖"连续取值一致性"的场景。已知命中 money_flow；
         理论上任何按连接缓存的数据都可能中招，用 pool_size>1 时需警惕。

  规避：
    - 要做差分/增量计算  -> 必须 pool_size=1
    - 只做独立快照读取    -> pool_size>1 可以，但要容忍抖动
    - 全市场批量扫描      -> 本身不依赖跨轮一致性，pool_size>1 问题不大

10.16 money_flow 字段结构：两套口径，各四档
--------------------------------------------------------------------------------
  client.money_flow.daily(code)   -> MoneyFlowBlock  (单只)
  client.money_flow.daily([...])  -> MoneyFlowBatch  (多只, .blocks)
  MoneyFlowBlock.records          -> tuple[MoneyFlowDaily]，通常最近 5 个交易日

  MoneyFlowDaily 共 18 字段：
    date_raw / date / total_amount / buckets(16) / raw(21) / record_hex
    main_net / main_ratio
    main_super_large_net / main_large_net / main_medium_net / main_small_net
    main_buy_net / main_buy_ratio
    main_buy_super_large_net / main_buy_large_net
    main_buy_medium_net / main_buy_small_net

  【关键】这是两套独立口径，不是同一数据的两种算法：
    主力口径 main_*        用 buckets 的 0/1, 4/5,  8/9,  12/13
    主买口径 main_buy_*    用 buckets 的 2/3, 6/7, 10/11, 14/15
  两者数值不同（实测同一时刻超大单：主力口径 -0.8591亿 vs 主买口径 -0.3666亿）

  官方公式（已逐位验证吻合）：
    main_super_large_net = (b[0]  - b[1])  / 50000 * total_amount
    main_large_net       = (b[4]  - b[5])  / 50000 * total_amount
    main_medium_net      = (b[8]  - b[9])  / 50000 * total_amount
    main_small_net       = (b[12] - b[13]) / 50000 * total_amount
    main_buy_super_large_net = (b[2]  - b[3])  / 50000 * total_amount
    main_buy_large_net       = (b[6]  - b[7])  / 50000 * total_amount
    main_buy_medium_net      = (b[10] - b[11]) / 50000 * total_amount
    main_buy_small_net       = (b[14] - b[15]) / 50000 * total_amount

  实测恒等式（5 只股票全部精确成立）：
    main_net     = main_super_large_net + main_large_net
    main_buy_net = main_buy_super_large_net + main_buy_large_net
    四档合计 ≈ 0（零和），中单+小单 = -main_net
    => "主力" = 超大单 + 大单，"散户" = 中单 + 小单，互为对手盘

  【能还原毛额】buckets 是公开字段，存的就是买入值/卖出值分开的原始数。
    文档只暴露净额字段，但主动买/主动卖可以自己算：
      主力口径 超大单 主动买 = b[0]/50000*total_amount
                     主动卖 = b[1]/50000*total_amount
    实测可完整还原 四档 x (净额/主动买/主动卖) = 12 个字段。

  使用提醒：
    1. buckets 单个数字是无量纲分档值，别直接当金额（要 /50000*total_amount）
    2. main_ratio = -9.19 表示 -9.19%，已 ×100，别再乘
    3. 位运算之外，字段是"当日累计值"

11.1 全市场五档 3 秒轮询（盘中监控）
--------------------------------------------------------------------------------
  from concurrent.futures import ThreadPoolExecutor
  from eltdx import TdxClient

  BATCH, THREADS = 100, 16

  with TdxClient.from_hosts(pool_size=THREADS, probe_hosts=False, timeout=8) as c:
      codes = list(c.codes.all_a_shares())
      batches = [codes[i:i+BATCH] for i in range(0, len(codes), BATCH)]

      def sweep():
          out = {}
          with ThreadPoolExecutor(max_workers=THREADS) as ex:
              for page in ex.map(lambda b: c.quotes.refresh(b, cursors={}), batches):
                  for r in page.records:        # r.buy_levels / r.sell_levels 各 5 档
                      out[r.full_code] = r
          return out

      sweep(); sweep()                          # 预热连接池（必须，盘中 ~13s）
      while trading:
          snap = sweep()                        # 全市场五档，盘中 ~0.94s
          # 只处理有变化的（约 23.7%）
          time.sleep(2)                         # 3 秒一轮

  性能预期：
    扫描耗时   盘中中位 0.94s，最坏 1.28s
    占空比     31%
    压强       约 19 req/s
    召回率     93.9%
    内存       约 14 MB

11.2 关键参数
--------------------------------------------------------------------------------
  批量大小     100（0x0547 硬上限，实测 100 不触发静默截断）
  线程数       16（8 也可；再高收益递减）
  pool_size    与线程数一致
  轮询周期     3 秒（数据源天花板，更快无收益）
  预热         NOT optional，必须在开盘前 5 分钟完成

11.3 单只/少量股票高频盯盘
--------------------------------------------------------------------------------
  只要盘口：c.quotes.refresh(codes, cursors={})     ~60ms
  只要价格：c.quotes.get_snapshots(codes)           ~46ms
  100 只以内一次调用即可，无需拆批。

11.4 【重要】不同数据的刷新节奏不同，别用同一个循环
--------------------------------------------------------------------------------
  各接口实测的刷新间隔（同一连接、同一时段）：

    接口            数据              刷新间隔
    ---------------------------------------------------
    quotes.refresh  五档盘口           ~2.9 秒      <- 快
    quotes.refresh  价格/成交量        ~2.9 秒
    trades          逐笔成交            ~3.0 秒
    money_flow      资金流四档          ~30-40 秒    <- 慢一个数量级

  正确做法是按各自节奏分开轮询：

    while trading:
        book = c.quotes.refresh(codes, cursors={})   # 3 秒一次
        if now - last_flow >= 30:
            flow = c.money_flow.daily(codes)         # 30 秒一次，pool_size=1
            last_flow = now

  [警告] money_flow 必须 pool_size=1（见第 10.15 条多连接陷阱）。
         资金流用 3 秒轮询是纯浪费——90% 请求拿回完全相同的值。

11.5 什么时候不该用 eltdx
--------------------------------------------------------------------------------
  - 需要亚秒级（<3s）刷新        -> 免费 Level-1 做不到，需商业 L2
  - 需要十档 / 逐笔委托          -> 免费源没有
  - 需要实时推送（服务端主动）   -> 实测不可用，只能轮询
  - 需要历史数据仓库             -> eltdx 是查询客户端，非数据管道
  - 需要资金流亚 30 秒刷新       -> 0x0ffc 就是 30~40 秒，免费源拿不到更快
  - 长期高频打同一批公共主站     -> 不礼貌，可能限流封 IP
